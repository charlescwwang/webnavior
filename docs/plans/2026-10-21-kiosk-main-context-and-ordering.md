# Kiosk Main 情境與點餐操作整合修改計畫

日期：2026-10-21。狀態：階段 1–4 的本機程式／瀏覽器驗證完成，並依後續授權分批 commit；舊測試 mock 差異已修正。尚未部署，真實模型／實機效能另行驗收。

本計畫合併本輪已討論但未完成的改善：Main 完整菜單、每輪最新情境、交接保留需求與解析原因、有效問題生命週期、別稱解析、商品及操作授權、回覆與本輪需求一致，以及刪除動畫與返回菜單。已完成的局部防錯保留，不能把它們當成整體驗收完成。

## 範圍與不變條件

- 修改 Order Menu、Stage Kiosk、Server 的 Main 對話與操作流程。
- 保留 Jev 作有限意圖辨識及 Main 分流；不改分類順序、信心門檻，不增加 Jev 檢查輪次。
- 保留 Eventa window-message、原有推薦／combo 及多工具操作能力；Stage Web、大麥頁面與新的瀏覽器通訊方案不在範圍內。
- 沿用 Valibot、既有工具驗證、版本與授權機制，不引入新套件或另一套訂單資料庫。
- 手機填寫或明確略過之前，不做菜單／訂單操作；店家服務資訊仍可回答。
- 商品理解可以有彈性；新增、更換、刪除及付款必須有對應顧客需求與成功回執。
- 未確認的商品不能用其他品項代替。換模型、完整菜單、查詢成功都不構成購買授權。
- 不自動重試失去回執的寫入，不因刷新情境而恢復已消耗或失效的確認授權。

## Main 情境資料契約

新增 host-only `kiosk_conversation_context`；與 Jev 的 `kiosk_fast_path_context` 分開，避免完整菜單擴大 Jev 輸入或改變候選。原有 `kiosk_interaction_state` 其他用途保留，不拿它目前的不完整摘要冒充完整快照。

### 快照

| 欄位 | 規則 |
| --- | --- |
| contextId、capturedAt | Menu 產生快照識別與取得時間；時間不是授權依據 |
| revisions | menu、cart、selectedItem、checkout，以及已使用的 recommendation／seating 版本；沿用現有計數，不另造版本系統 |
| entry、phase、screen | entry 為目前電話步驟是否完成，不含電話號碼；由 orderingReady 與目前機器狀態產生，不從歷史推斷 |
| catalog | 完整語意菜單：ID、正式品名、別名、分類、介紹、價格、選項／預設與必填、已提供的成分資料及供應／頁面狀態。未知與不可用分開，不把缺資料視為安全或有貨 |
| cart、selection | 每筆真實 lineId／itemId、份數、客製、金額、目前用餐方式與選餐；與 revisions 同次取得 |
| checkout、payment | 目前發票／桌位／付款階段、合法選擇及已確認結果；支付方法 ID 沿用目前 POS 能力，不把實際 LINE Pay／街口等選擇壓成舊 card／mobile 分類；僅含當輪必要且允許的資料，不含憑證、卡號或交易機密 |
| questions | 最多一個目前有效問題；暫停／完成／失效問題另外分類，不冒充 waitingFor |
| requests | 目前任務與相關暫停需求的原句、效果、對象及狀態；歷史對話維持獨立 |
| capabilities | 目前可讀／可操作種類與對應既有工具名稱；僅說明目前合法性，不自行擴張本輪授權 |

Menu 在同步區段讀取訂單／選餐／checkout，完成後再回傳，避免組合不同版本的快照。檢查中若必要外部資料刷新發生版本變動，重新取得一次；仍不一致回報 unavailable，不輸出拼接快照。

手機階段不把完整菜單送給模型，不透過 Main 提前介紹餐點。完成填寫或明確略過後才提供完整菜單；一般店家服務資訊仍由店別設定提供。

圖片、SVG、原始 POS 回應與無關 metadata 不進模型。目前來源菜單為 7 項，原始 JSON 緊縮後 UTF-8 為 3,528 bytes，介紹最長 18 字；這是來源資料量，不是完整模型 prompt 或 token 數。

200 項與整個情境 UTF-8 256 KiB 是 schema 的異常資料拒收上限，不是模型輸入目標，也不是效能合格標準。Main 不直接取得上限內的所有原始欄位。不得靜默截成前幾道菜；序列化包含 complete:true、itemCount 與 menuRevision，超限回報 context-unavailable，不讓 Main 把部分菜單當全部。若未來店家超過上限，另外規劃較大菜單策略，不在本期偷偷改成僅送前幾項。完整 prompt 能否放入設定模型及是否夠快，仍需量測，不以 bytes 假充 token 容量。

Server 每次模型請求都實際組裝所需的完整菜單；只傳 menuRevision 或只在 Server 快取資料，不能假設模型記得前一輪。可按版本快取純序列化結果，但仍須將內容放入每次模型輸入；不引入新的快取基礎設施。

### 模型輸入精簡與延遲限制

完整代表品項完整，不代表欄位越多越好。Main 使用明確欄位清單投影，不可把快照／POS 物件直接 JSON.stringify 後整包塞入。標準輸入保留每道菜的 ID、品名、別名、分類、價格、簡短介紹、客製選項與供應狀態；飲食及成分事實以必要結構表示，不混入大量宣傳或重複敘述。

- 商品介紹優先使用店家簡短介紹，以 120 字作一般敘述預算；更長的行銷介紹不直接傳送。不能把必要的選項限制、過敏／成分未知或供應條件截掉來省字，這些資訊應在結構化欄位明示。額外細節僅在相關問題需要時由現有資料工具取得。
- 同一次模型請求只放一份目前菜單及一份最新狀態。接續時替換快照，不把每輪快照累積進歷史；工具回執依既有 compaction 保留本次必要結果，不重複塞入完整分類、成分字典及相同商品詳細資料。
- 歷史以理解本輪的最近對話與有效未完需求為主，較早內容沿用 session history 工具；不為整理歷史、縮寫菜單或檢查每一輪額外呼叫模型。
- checkout／付款時只附當前必要流程資料，不附已失效的桌位、手機問題與整份問答生命週期紀錄；完整菜單本身仍維持一次，避免使用者中途提出新餐點時喪失理解資料。
- 純店家資訊、招呼及手機階段不帶菜單；菜單／訂單任務才使用完整語意菜單。能力清單與實際 tool definitions 不重複長篇描述，工具只提供合法且與本輪授權相交的集合。
- UI 圖片、來源網址、SVG、原始供應商欄位、內部日誌及追蹤 metadata 不進模型。correlation IDs 只在關聯所需欄位出現，不在多個提示段落重述。
- Server 序列化快取可減少本機處理，但不算已降低模型輸入量或推論時間；未實測的 provider prompt cache 不納入效能承諾。

效能驗收以同一模型、設定、案例及相近歷史長度比較修改前後：記錄每輪 input tokens（provider 有提供才使用）、首次文字／工具輸出的 p50／p95、任務完成時間、模型輪數，以及各區段 bytes／字元數。沒有 token usage 時明示缺測，不能把 bytes 換算成精確 token。量測分開列新鮮度讀取、網路／模型等待與動畫時間，避免把 UI 動畫算成 Main 變慢。

在階段 0 建立基準後，先給欄位精簡方案量測，再納入其他變更；若簡單需求等待時間明顯惡化，需找出重複資料或多餘查詢並調整，不能僅因正確率提升就宣告完成。先前 256 KiB 上限不能拿來合理化冗長輸入。效能測試不新增模型語意關卡，也不透過漏掉商品、必要限制或最新狀態來換速度。

### 交接與任務結果

| 欄位 | 規則 |
| --- | --- |
| taskId、utteranceId | 沿用 Kiosk 任務／語句關聯；同輪接續不可換成歷史任務 |
| sourceUtterance、relatedFragment | 保存原句；只有既有已驗證關聯的片段可承接，不拼接無關歷史 |
| proposedIntent | Jev 或 Application 已確認的有限效果；沒有則標示 unknown，不捏造意圖 |
| resolution | resolved、ambiguous、unmatched、target-absent、unavailable、stale、unrepresentable 等可區分結果；來自 Application，不是讓 Main 重填的事實 |
| target | 商品與購物車對象分開，包含已確認 IDs、候選及對象缺失原因；catalog 有水餃不等於 cart 有水餃 |
| constraints、authority | 既有價格／飲食條件、readOnly、可執行效果與未決商品確認；刷新事實不能放寬條件或消耗確認 |
| receipts | 本輪已接受、未接受或結果未明的操作與其 task／call 關聯；寫入未知不得重放 |

在 Menu 對 REMOVE_ITEM 已確定效果且確切商品對應不到購物車時，回傳 `target-absent` 與當前購物車版本，直接產生「目前購物車已沒有水餃」。不能宣稱第二次又刪除、改刪牛肉麵或以查菜單補救。多筆同名仍需釐清；不確定是哪一道餐點也不能回報已不存在。

這是目前狀態的無需修改結果，不是永久封鎖該品項：顧客重新加入水餃後，新的刪除需求仍可移除新 lineId。

## 每輪刷新與操作時序

1. Kiosk 確認當前訪客、互動 turn、iframe document／connection 仍有效。
2. 取得 Menu 快照，將有限交接資料綁定 taskId，計算本輪授權與目前能力的交集。
3. 將完整情境、獨立歷史及合法工具送 Main。提示優先序為目前事實／授權、有效問題、本輪需求、歷史線索；角色設定不能覆蓋操作規則。
4. 模型回傳工具後，先核對該工具屬於本輪提供的工具集合，再由 Menu 對目前版本、對象及授權驗證。模型沒收到的工具不能因 iframe 有註冊就執行。
5. 同批多工具循序執行。獨立且已授權的操作可承接同 task 自己造成的版本進展；外部觸控、其他 turn 或選餐變動不能被當成自己的進展自動重新授權。付款／破壞性確認票不得重綁版本。
6. 收到回執後，重新取得情境與工具，再送 Main 接續。唯讀也不能無限重用舊情境，一般寫入接續也不能省略狀態。
7. 呈現最終回覆前，核對 turn、任務、問題與必要版本；舊請求不能覆蓋新問題或新畫面。

沿用目前一輪總時限及工具上限，不為每輪刷新重置倒數。刷新失敗不自動重送已執行寫入；若已有成功回執，保留並告知已完成部分，未完成部分以自然用語交代。停止、重整、END 或切換訪客會撤銷本輪情境；已送出的外部操作仍需收斂其結果。

初始直接輸入、Jev 轉交、Jev 不可用與 Main 工具接續都走同一讀取規則。持續的同輪主題與授權不從舊 decisionState 推導，也不只靠每次附上一句「以最新為準」。

KioskScene 提供一個真正讀取 Menu 的 `prepareRound` 回呼給現有 recording.send 流程，初始與每輪接續都 await 它；回傳同一份 context 與目前可用 tool definitions。不另造沒有狀態責任的 service／Dependencies 包裝。主動招呼沒有點餐任務時沿用既有服務互動流程，不因新契約自動讀菜單或獲得修改權。

### 階段與工具規則

下表只定義目前合法能力，還要與本輪需求授權相交；Server 不自行根據歷史補出合法操作。

| 目前階段 | Main 可取得的工具範圍 |
| --- | --- |
| customer_entry | 僅既有 session history；填電話／略過由 host 擁有，不提供菜單或訂單工具 |
| ordering | 依本輪效果提供菜單呈現／讀取、商品確認、訂單操作、用餐方式、桌位及可合法啟動的結帳工具；讀取需求維持 readOnly |
| configuration／clarification／meal_confirmation | 讀取資料及目前問題允許的效果；新需求須先走既有 host 撤銷或暫停問題的路徑，不把 Main 工具呼叫當成回答確認 |
| pending_confirmation | 可讀及釐清；確認／取消走現有一次性票據；新需求先撤銷舊票據，不並行執行另一筆寫入 |
| checkout_membership／invoice／tax_id | 各自當前可選操作、必要唯讀與合法返回；已完成階段不再提供舊工具 |
| checkout_payment_select | 目前實際可用支付方式及必要唯讀；尚未取得授權不可提交或宣稱付款 |
| payment_locked／pending／uncertain | 既有安全查詢與狀態說明；不提供重新付款、清空、改單或重開訂單能力 |
| checkout_complete | 已確認結果及目前合法後續；新一輪須走 host 的明確流程，不因一句附和建立新訂單 |

具體工具名稱以 Menu 註冊與現有 authorize 為準，不為表格中的「狀態查詢」虛構未實作工具。phase 與 screen 分開：畫面仍顯示菜單，不代表付款鎖定可以解除。

## 問題與需求生命週期

沿用 questionHistory、pendingConfiguration、suspendedConfigurations、mealClarification 及目前 taskId；補齊語意，不新增平行的流程資料庫。

| 事件 | 問題與需求的變化 |
| --- | --- |
| 發出並實際呈現問題 | 記錄 questionId、目的、對象、所需版本與期限，才能成為有效 waitingFor |
| 有效回答 | 只執行該問題明示效果；完成後退休問題，不順便授權其他操作 |
| 明確新需求 | 舊問題離開前景；保留或失效依版本與需求種類判定，不視為同意／取消舊餐點 |
| 新需求完成 | 不自動恢復僅推測出的舊話題；既有明確保留的未完成餐點流程，可在核對版本與對象後依既有規則恢復並清楚提示 |
| 顧客要求繼續舊需求 | 重新驗證保存的效果與對象，必要時重問，不能沿用失效授權 |
| 修改訂單／切換自取／重整／到期 | 使依賴舊版本的問題失效；不得留在 Main 的有效問題區 |

特別保留「更換」的效果：`改排骨飯` 的確認不能退化成只確認是否新增排骨便當。原 lineId 不明時先釐清原餐點；新品項不明時確認新品項；更換未成功前保留原項目，成功後才回報已更換。

## 完整菜單與名稱解析

1. `menuIdentity` 集中目前名稱／別名／片段辨識；menu_get 與 Fast Path 不再各自定義一套。
2. 精確名稱或店家別名可對應現有商品；共同別名匹配多項時保持歧義，不挑第一個。
3. 片段與分類只能形成候選，不因唯一候選升級成已確認商品。
4. Main 依完整菜單理解 `排骨飯` 等未列出的說法，可提出真實商品候選，不把自己的推論寫進店家 aliases。
5. 增加受限 `menu_confirm_item`，由 Main 提交已在目前完整菜單中的候選 ID，讓 Menu 建立固定確認問題。它不能新增餐點；問題必須保留原 task、效果、替換 lineId、限制與版本。不能向 Main 開放 host-only clarification 工具。唯讀查詢不因此建立購買問題；效果仍未知時只能明示提出待確認效果，不能先建立可執行授權，顧客確認必須涵蓋這個效果而非僅確認品名。
6. 只有顧客有效確認後，才可依原效果建立一次可執行計畫；若是更換仍走既有帶 replaceLineId 的原子操作。確認新品項不能順便決定原餐點或忽略客製需求。
7. 沒有合適候選時，以完整菜單事實說明查不到該品名，並釐清是否指其他餐點；不把鱔魚意麵解成牛肉麵，不擴張條件代找商品。

既有 targetItemIds 防錯改為明確的「確認狀態與合法目標」；不能一方面把完整菜單給 Main，一方面只允許前置字面匹配到的品項而永久擋住合法別稱。也不能反過來開放全部菜單 ID 寫入。無字面匹配的需求不因此獲得任意新增權；有效短句與既有問題仍使用已驗證的對象，未知對象先確認。

目前 requireMenuRead／hasMenuReply／提示詞中「餐點事實一律先查工具」要一起修正：最新完整快照可支持品名理解與事實回答，不強迫為理解名稱再做一次字面查詢。顧客要求看菜單、推薦或呈現查詢結果時，仍須以現有呈現工具同步畫面；新快照不是顯示完成回執。過期或缺完整菜單時不能宣稱品項／價格已確認。

## 回覆與本輪需求一致

把執行結果分為 completed、already-absent、needs-confirmation、partial、rejected、uncertain，附上本輪 task、效果與對象；不只根據「曾經呼叫成功工具」採用文字。

- 操作完成敘述以同輪成功回執為準；failed、pending、uncertain 不可說完成。
- 刪除水餃的需求以移除或已不存在結果完成，查排骨飯不能完成此需求。
- 純查詢維持 readOnly；查詢成功、完整快照及新工具能力都不能提升為修改訂單的權利。
- 比較、推薦與複合需求可以有多個合理查詢對象，不能用「查詢字串必須等於原句」代替語意驗證。
- Main 的自由回覆仍可能偏題。可確定驗證的是 task／效果／商品與操作結果的關聯，不宣稱程式可完整證明任意自然語言語意正確；語意相關性另外用模型重播驗收。
- 固定問題只組合一次；內部工具錯誤留在 Trace，顧客看到自然且符合已完成事實的回覆。

## 刪除操作與 Vue 呈現

不改用 DOM 自動點擊，也不重做游標動畫。沿用 announce／animateAction 與 OrderReview 的 registerControl：

1. Menu 驗證可移除的確切 lineId 與目前操作階段。
2. 必要時透過現有 onReviewRequested 顯示購物車；等待 DOM 更新，對應 lineId 的移除按鈕註冊完成。
3. 使用由 lineId 編碼的穩定 controlId 定位與動畫，避免只指向泛用 cart。
4. 動畫完成後再驗證 lineId／版本，執行一次 removeFromCart，更新購物車。
5. 成功後返回菜單、刷新情境，才呈現成功回覆。動畫不額外觸發第二次 DOM click。

單純 Agent／語音刪除在 ordering 成功後返回菜單。觸控移除維持原購物車操作習慣；combo／複合操作由同輪操作序列決定何時收尾，不在每個中間工具都強制跳頁。checkout、payment locked 或 uncertain 不為動畫繞回菜單。找不到控制項時不得無聲宣稱動畫完成；回報呈現失敗，尚未開始的刪除不執行。已刪除但返回畫面失敗，必須保留成功回執並區分呈現失敗，不能重刪。

元件責任：OrderReview 只呈現 lines、註冊控制項並 emit remove；App 接線 review／menu 畫面與既有游標；Menu runtime 擁有操作時序與訂單結果；KioskScene 只呈現已核對回覆。沿用 Composition API，不新增第二份 cart 或以 watcher 猜操作完成。
