# Webnavior 管理體驗與角色分工

## 目標

Webnavior Control Center 的首頁應協助人員判斷「現場是否正常、目前顧客會遇到什麼、下一步該做什麼」，而不是呈現底層 Profile、Provider 或網址設定。技術整合仍必須可管理，但只能由適當角色在明確的系統管理流程中操作。

## 用語

| 原有技術用語 | 管理端用語 | 對使用者的意義 |
|---|---|---|
| Profile | 互動體驗 | 一套顧客會遇到的 Kiosk 行為與內容。 |
| Profile 草稿 | 體驗草稿 | 尚未套用至設備的編輯內容。 |
| Profile 發布版本 | 已發布體驗 | 正在設備上使用的不可變版本。 |
| interactive service URL | 互動服務網址 | Kiosk 顧客畫面內嵌的服務頁面。 |

內部資料表與 API 可以保留 `Profile`，但一般 UI、通知與操作說明不得把它當作主要名詞。

## 角色與任務

| 角色 | 預設首頁 | 可以完成的任務 | 不可見或不可操作的內容 |
|---|---|---|---|
| 店務管理者 | 設備狀態、目前已發布體驗、待處理提醒 | 查看設備、發起現場驗證、閱讀結果 | Provider、模型、服務 URL、系統提示詞、帳號角色 |
| 內容管理者 | 體驗草稿、待發布內容、預覽 | 編輯顧客文字、選擇核准的互動服務、送出發布申請 | 金鑰、模型、設備註冊、系統測試 |
| 系統管理者 | 系統健康、整合狀態、待發布項目 | 管理服務整合、建立沙盒測試、發布、管理角色與設備 | 無；但不應被迫處理日常店務內容 |

現行全域 `admin` 暫時對應「系統管理者」；現行 `site_admin` 暫時對應「店務管理者」。內容管理者的正式授權模型在帳號管理功能完成時才加入，避免先建立沒有指派與稽核介面的角色。

## 後續 Kiosk 營運設定原則

- 店務管理者不應調整 VAD threshold、視覺 cadence、System One 決策門檻、模型或 Provider URL。這些參數由系統管理者以版本化 policy 管理，Kiosk 依現場噪音、推論耗時與決策結果採取受限的自動調整。
- Provider、模型、URL 與憑證仍是系統管理者的動態 Server 設定。對話、視覺、ASR 與 TTS 各自維護多筆能力專屬 Provider Profile；相同網址不能跨能力共用。每項能力只有一筆已驗證的啟用選擇，切換後須明確套用才會由下一次請求生效，不要求重啟 Kiosk 或 Server。Dasein System One 屬於獨立決策服務，另行保存 profile、readiness 與啟用狀態。Kiosk 不會下載模型或取得憑證，金鑰只會加密寫入 Server 的 runtime 設定。
- 實際 POS 或店家菜單整合暫不納入目前 POC。日後由領域服務將其正式商品、庫存與訂單能力實作為原生 WebMCP；Kiosk Host 不建立廠商專用 adapter，也不管理 POS 資料。
- VRM 待機動作可作為發布版 Profile 的獨立 `.vrma` 資產；招呼、推薦與完成點餐的 one-shot 動作需在後續設計為有限、可驗證的 action mapping，不能讓角色卡文字或 LLM 直接指定檔名或 URL。

## 首頁資訊層級

所有角色的首頁先回答三件事：

1. **是否正常**：設備可用性、最近一次發布結果、需要處理的問題。
2. **目前呈現什麼**：已發布互動體驗的名稱、顧客看到的助手名稱、適用店別。
3. **下一步做什麼**：以角色允許的單一主要動作呈現，例如「進行現場驗證」或「檢視待發布內容」。

名稱必須附有語意標籤。例如「顧客看到的助手名稱」而非只顯示一段任意文字；「內部識別名稱」必須明確標示不會出現在 Kiosk 顧客畫面。

## 三種驗證流程

| 流程 | 操作者 | 目的 | 不可做的事 |
|---|---|---|---|
| 體驗預覽 | 內容管理者、系統管理者 | 檢查顧客文案與嵌入頁呈現 | 不呼叫實體 Kiosk、不發布 |
| 沙盒測試 | 系統管理者 | 驗證服務串接、模型與錯誤處理 | 不改變正式設備、不留下顧客互動紀錄 |
| 現場驗證 | 店務管理者、系統管理者 | 在指定設備確認已發布版本 | 不顯示 Provider、金鑰或系統提示詞 |

## 交付順序

| 順序 | 工作項目 | 狀態 |
| --- | --- | --- |
| 1 | 以「互動體驗」取代管理端的 Profile 用語，改用結構化編輯器並移除 JSON 編輯流程。 | 已完成 |
| 2 | 將首頁改為營運摘要，呈現設備、已發布體驗與下一個可採取的動作；技術設定移至系統管理流程。 | 已完成 |
| 3 | 建立唯讀體驗預覽；草稿會在獨立 Kiosk iframe 呈現，不發布也不使用正式設備。 | 已完成 |
| 4 | 建立系統管理者專屬的模型／服務整合與每店模型政策；店務與內容角色不會取得這些技術設定。OpenAI-compatible TTS 連線可設定 voice，預設 `zh-TW-HsiaoChenNeural`。 | 已完成 |
| 5 | 建立系統管理者專屬沙盒測試與店務管理者的現場驗證流程。 | 待實作；需要設備健康、測試執行與稽核資料。 |
| 6 | 完成內容管理者的正式帳號指派、送審／發布權限與稽核紀錄。 | 待實作；目前角色能力已在 Kiosk 管理 API 實作，開發用帳號可用來驗證介面，但尚未提供正式帳號指派與稽核流程。 |

## 本輪實作邊界

- 每位系統管理者現在可發布一份「新店別預設互動體驗」。新店別建立時會複製該管理員最新發布快照，建立自身的 draft 與 immutable release；既有店別不會被模板更新覆寫。店別 release 會記錄模板來源、店別 revision、父版本與變更範圍，方便辨識本店客製版本。

- Kiosk 體驗快照現在可引用伺服器擁有的 VRM 或 Live2D 角色資產；上傳的原始檔案是部署期資料，不納入 git。Kiosk 只會依已發布快照下載及快取角色資產。
- 管理端保留內部 `Profile` 資料模型與 API 名稱，以維持既有版本化發布契約；面向使用者的頁面改以「互動體驗」描述。
- 系統模型頁的 OpenAI-compatible TTS 連線保留自己的上游 model、endpoint、選填 API key 與 voice。voice 預設為 `zh-TW-HsiaoChenNeural`，由 Server 以 MP3、speed `1.0` 呼叫上游；Kiosk 不會取得這些設定或任何 Provider 憑證。
- 體驗草稿可設定 voice-only 對話模式。已發布後，Kiosk 隱藏文字輸入並依已獲准的麥克風權限啟動 VAD；這不是一般內容管理者可見的 Provider 設定。
- Kiosk 完成 ASR 後，先交由 System One 以目前顧客可見的有限 Fast Path 語意候選做決策。回傳的 intent 只能由應用程式對映回既有 WebMCP 操作與已驗證參數；System One 不能建立任意 cart、POS 或瀏覽器命令。需要解釋、複合操作或 System One 暫時不可用時，當輪轉寫會自動交給 Main Agent；未完成語句、釐清回覆與背景語音不會自動轉交。
- Server 會以既有 OTel product counter 匯總不含文字內容的 Fast Path 決策結果與服務健康狀態，不保存語音向量、設備或顧客識別資料。這是現場驗證與後續 policy A/B 的量測基礎，不代表目前已向店務管理者暴露技術調參。
- 管理端已提供 Site 範圍的訪客使用歷程：會話依日期／時段分組，閱讀頁將對話與行為摘要分開；顧客語音轉錄可播放原始 WAV，活動可播放對應觸發短片，連續影片則按需載入。管理者可單筆或批次永久刪除會話及附屬媒體。它服務內部 POC 的營運回顧，不構成尚待實作的沙盒測試或現場驗證流程。
- Kiosk 設備清單支援目前店別範圍的全選與批次停用；批次刪除只會納入已停用設備。每台設備維持既有的個別授權與稽核，操作回報成功及失敗清單，不會回復已成功的設備操作。
- 本機開發預設連接埠固定為：管理端 `5167`、Server API `5168`、Kiosk `5169`、點餐服務 `5166`。這些固定來源也用於登入 callback、CORS 與 WebMCP allowlist。
- 開發用 Webnavior 帳號由 `pnpm --filter @proj-airi/server seed:test-accounts` 建立。它僅可在非 production 環境使用，不取代正式帳號與角色管理功能。
