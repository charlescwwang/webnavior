# 餐廚點餐限定模型：JEV / Main Agent 改善選項

日期：2026-10-09。範圍：現有程式、凍結測試與外部第一手研究的評估。沒有修改正式流程、安裝套件、訓練模型或呼叫部署中的模型；以下提案尚未實作或證明改善。

使用者目標是讓 JEV 可靠處理更多餐廚點餐，避免 Main Agent 的網路、排隊、多輪工具與模型生成等待。這些成本都應納入，不以查明哪一項最慢作為開始改善的前提。Main Agent 慢是設計限制；目前不推估換模型後的秒數。

## 結論

建議先把問題收斂成「根據目前訂單狀態，辨識顧客這一輪想做的有限操作」，評估短輸出語意解析與可靠澄清，再考慮微調。Main Agent 可處理少數點餐內的複雜語句，但不應成為每次不確定都必經的慢路徑。這是針對使用者硬體與產品範圍提出的設計推論，尚待本機資料驗證。

**優先方向：JEV 理解有限需求，既有點餐程式負責完整執行與對帳；Main Agent 留作少數點餐內的例外。** 不新增一串分類器、審核器和大模型的必經鏈，也不把自由客服能力帶進來。單純微調分類標籤不能填補漏單記錄或替換執行的缺口。

## 現有證據：誤判至少有四種來源

主要依據：[凍結比較報告](../../test_prompt/turnClassifierPoc/report.md)、[決策流程說明](2026-10-02-jev-decision-review.md)。各實驗是不同合成挑戰集，不能合併成營運準確率。

| 類型 | 已觀察到的例子 | 判斷與改善位置 |
| --- | --- | --- |
| 語意分錯 | 「想吃麵」選 INCOMPLETE，信心 .7969；「先看看你們的麵好了」也有高信心 INCOMPLETE | 提示、標籤及模型能力需要改善；單純提高信心門檻不足 |
| 需求被壓成單一意圖 | 「牛肉麵一碗＋排骨便當一個」選 ADD .8661，程式問兩者擇一 | 必須區分兩個新增、二選一、同品項多份；單一 ADD 不能代表整句已理解 |
| 缺少需求與完成結果對帳 | 「你沒有點到我的牛肉麵」三條測試路徑均未完成補救；較大模型也重新問數量或同意 | 需要原先需求、數量來源、授權與實際 receipt 的關聯，不能只看本句或 cart 是否有品名 |
| 執行流程不完整 | Main Agent 替換餐點重試中，四回合後刪了便當但沒加牛肉麵 | 替換應由點餐程式承擔完整性；不能只驗每個工具個別合法 |

也有非模型缺口：「總共一個人而已」在有待答人數問題時沒有產生人數候選。微調或改 prompt 無法選出程式沒有提供的候選。

已驗證但不應直接採用的方向：

- 44 句正式決策對照：契約符合 baseline 17/44，分層 13/44；拒絕由 8 增為 28。更細的七類 gate 並未改善整體服務，多需求與漏單正確交接皆 0/4。
- 同模型五題盲解析，26 句完整 profile 0/26；多需求數量與欄位重複互相矛盾。不是「多問幾題」就能組成可靠解析。
- 小 encoder 八類測試：frozen head 58/80、SetFit 59/80。暖機約 8ms 有低成本潛力，但高信心複合句仍錯；這不是點餐完成率，也不證明微調顯著勝出。
- 16 句三路比較：JEV 前段非 safeOnly 自動完成 6，生成提案 9；Main Agent 首次 12 筆 settled 中完成 6，另 4 筆服務中斷。JEV 沒續跑 Agent、提案使用實驗 binder，不能直接比較成正式 pipeline 優劣。

程式核對：[prompt.ts](../../apps/server/src/services/domain/kiosk-interaction-decision/prompt.ts) 已有餐廚限定、MULTI_ACTION、分類瀏覽與未完成話語的規則；不能把問題當成「忘了寫 prompt」。[index.ts](../../apps/server/src/services/domain/kiosk-interaction-decision/index.ts) 對 INCOMPLETE 直接返回，低信心高風險操作則拒絕；[Host](../../apps/stage-kiosk/src/services/kiosk-fast-path.ts) 保留未完成片段最多三秒。這解釋錯分後為何可能沒有恢復，但不證明模型錯分的原因。

## 優先改善：把餐廚流程交給程式完成

先沿用 [kiosk-intents.ts](../../apps/order-menu/src/kiosk-intents.ts) 的 deriveDecisionContext、resolveIntent、compileOperationPlan、authorize 與 [webmcp.ts](../../apps/order-menu/src/webmcp.ts) 的真實收據、revision、確認規則；不要另寫一套訂單狀態機。現有 [需求提案實驗](../../apps/server/tests/experiments/generativeRequirements.ts) 及 [binder](../../apps/server/tests/experiments/assistantFixture.ts) 只能作為接口與反例參考，不能直接升格正式功能。

建議把共同的「顧客需求及完成狀態」放在既有點餐 domain 內，供 JEV 與 Main Agent 共用：每項需求保留原文來源、目標、數量／條件的歸屬、必要的歷史或問題引用、顧客授權、對應執行結果，以及完成／待釐清／不支援／失敗／結果不明狀態。它不是再加一個模型。

這個設計有兩個限制：程式不能憑空發現模型完全漏掉且未被記錄的需求；模型自行填寫「全部完成」也不能作為完成證據。必須同時驗證解析覆蓋率與真正執行結果。

| 點餐情境 | 建議由 JEV 表達 | 點餐程式負責 |
| --- | --- | --- |
| 單品／多品項新增 | 各項需求、數量、各自條件；保留 AND/OR 差異 | 綁定真實菜單、檢查選項與版本；完整準備後執行並逐項記錄，避免把多選問成單選 |
| 改餐 | 舊目標、新目標與數量／條件 | 先驗新餐可成立，再提交本地 draft 替換；若不能保證原子性，明示未完成，不能先刪舊餐再等模型規劃下一步 |
| 漏單抱怨 | 指向先前需求的「核對／修復」，而非直接新增 | 比對尚有效且未撤銷的授權、receipt、最新 cart；已完成不重加，結果不明先核對，證據不足才釐清 |
| 「好／一位／第二個」 | 引用哪個有效問題或展示集合，或表示不確定 | 驗證問題用途、session、展示來源、版本與合法效果；不要自行猜授權 |
| 食材與價格條件 | 條件屬於哪一項餐點或哪次查詢 | 僅採店家資料與可用選項；未知如實說明，不為了少交 Agent 而忽略條件 |

本地購物車替換的原子性不代表 POS／支付可一起交易或回滾；支付結果不明仍保留既有鎖定及對帳政策。多品項有部分不支援時，先顯示逐項狀態並讓顧客決定是否只點可用部分，不默默完成子集合。

## 如何保留 JEV 的速度優勢

應比較兩個替代方案，而不是把兩者串成每輪必經流程：

1. **保留有限選擇 JEV**：釐清標籤與候選缺口，強化上下文對照與校準；簡單需求維持快路徑，缺失 slot 由現有畫面／固定問題釐清。複合需求仍須有可靠表達，不能只選 ADD 後宣稱完成。
2. **餐廚專用的短結構解析**：一次輸出整句需求與各自條件，直接交同一點餐程式驗證。這是可取代部分 JEV 決策的 adapter 候選，不是已證明更好的新必經層；先前生成提案與獨立 choice 實驗失敗仍須保留。

公開 [lookski/openjev core.py](https://github.com/lookski/openjev/blob/main/openjev/core.py) 以受限 next-token logits 做每題一次 forward，多題依序對相同 state 判斷。因此，一個 HTTP 包含多題不等於一次推論，也不自動保證跨題一致。此為公開參考實作，沒有核對實際部署 commit/backend，不能斷言現場完全相同。

若仍保留這種 JEV 形式，微調目標應對齊實際 state、題目、tokenizer/template 與答案 token；隨機排列選項，驗證模型學到語意而非位置。若改成生成需求 JSON，就應當成不同解析接口獨立比較，不能把一般聊天 SFT 成績當成 JEV 改善。

現有 Host 已有題數預算與部分 review timeout；新增工作的重點是每輪顧客可接受的總等待與可恢復出口，不能把技術上限當成體驗目標。不要固定每句先 JEV、多輪 reviewer、再 Main Agent；沒有必要的額外模型審核應以對照實驗決定是否移除。

Main Agent 接手時，只接有效點餐範圍內尚未解決的需求、必要原文、最新狀態與已有結果；減少重新查菜單、讀購物車及自由規劃。既有 Agent 已有對話／工具壓縮，不應宣稱目前完全沒做。較長角色描述、工具 envelope、本輪新結果被視為舊推薦禁用等可分別做 ablation，不一次刪掉必要資訊。確定操作結果優先由程式呈現，是否可省最後一輪生成需核對現有 Host 行為。

不確定是否向本機說話時，不直接交 Agent。已確認是點餐但缺欄位時，用短澄清與觸控選項恢復；完整句被錯判 INCOMPLETE 的恢復仍需驗證，不能以一個門檻或關鍵字當解法。超時後保留目前需求與完成結果，停止新的模型／工具工作；已發出的變更需先確認結果，不能重播。

## 微調順序與驗收

先完成共用需求／執行契約，再固定一批獨立 holdout，比較未微調 JEV、改善後有限選擇 JEV，以及可選的短結構解析。測試語義全對、receipt 全對與耗時，不能只驗 JSON。模型或套件選型應另列候選由使用者決定，本次不選定依賴。

若語意混淆仍是主要限制，優先微調 JEV 所使用的底層模型或餐廚解析 adapter；不是訓練 JEV 框架本身。訓練包含「目前狀態＋這句話＋有限需求／澄清」，尤其多品項、否定作用域、口語省略、漏單核對與同句不同狀態。Main Agent 微調放後面，針對有驗證收據的短工具軌跡、修正與停止條件；不直接模仿既有失敗軌跡，不訓練無關客服答案。可用較強模型離線產生待覆核資料，避免每次線上呼叫它。

微調同尺寸模型不能保證減少運算；加速收益若存在，應來自更少回合／輸入輸出，或經蒸餾驗證後可換較小基底。資料量以學習曲線決定，不先承諾幾百筆即可可靠上線。

建議下一個獨立單位先只處理「雙品項新增、替換、漏單核對」三個高價值家族，固定成功、拒絕、部分完成與結果不明的契約，再做隔離 replay；尚未授權需求不得因追求完成率而執行。舊測試保留為回歸，新測試用不同模板家族／菜單／ASR 變體。驗收要求是同等風險下提高無 Main Agent 的完整服務覆蓋，並降低全體端到端等待；不只讓更多請求提前拒絕。

## 建議比較的方案

以下是方案候選，不是已決定的套件或模型選型。

| 方案 | 適用點 | 主要限制 |
| --- | --- | --- |
| 保留 JEV，改善輸入狀態、標籤與拒絕策略 | 最先建立可重現基線，辨識究竟是資料、門檻、狀態或分類能力問題 | 單一意圖分類不能自動表達「兩個餐點、分別不同數量」或替換等複合操作 |
| 小型分類器＋槽位／候選解析 | 有限操作集合、較短固定輸出；可與現有模型做低成本對照 | 多意圖、否定作用域、指代仍需專門資料和明確狀態契約 |
| 小型生成模型輸出受限操作提案 | 一輪提取多品項、數量、客製化、修改目標與待澄清欄位 | 結構合法不等於內容正確；需驗證與對歧義拒絕，速度尚待實測 |
| Main Agent 限定點餐子任務 | 少數上述方案無法處理的點餐內複雜需求 | 多輪工具呼叫可能放大延遲；超時、執行一半與重試安全必須由執行層處理 |
| 微調／蒸餾專用模型 | 前述輸入與契約已穩定，但保留集仍存在系統性語意混淆 | 不能修復缺失狀態、錯候選、執行原子性或硬體容量；需要可靠標註與獨立測試集 |

建議模型只產出「提案」：操作類別、菜單候選、購物車目標、數量／選項、否定或修正、缺失資訊。程式驗證候選、目前版本、數量與選項，處理權限／確認並執行。確認、指代與待回答問題綁定明確的 pending state；不能用更長的自由文字歷史取代。

「牛肉麵跟水餃各一份」和「牛肉麵或水餃都可以」需要不同結構；「不要辣」和「不要牛肉麵」不能只靠同一否定標籤處理。「第二個」只在當前有效候選集合內有意義。這些是建議納入測試的語意對照例，不聲稱是已觀察到的本機故障。

不確定需要區分出口：缺欄位或歧義 → 用固定問題＋畫面選項澄清；點餐內確實複雜 → 受限 Main Agent；明確向本機提出範圍外問題 → 可用固定台詞簡短導回點餐；背景話語／對同伴說話 → 忽略。不能把背景話語一律變成店員回覆，也不必為這些情境呼叫大模型。

## 微調資料與評估設計

先凍結標籤與操作契約；將既有錯例依根因分開：ASR、候選漏召回、意圖、否定／修正、指代、槽位、狀態、執行及 timeout。資料輸入包含當前菜單候選、購物車版本與待澄清狀態；標註的是可接受操作或必須澄清，不是只有自然語言回答。

資料應覆蓋臺灣中文常見省略、同音 ASR 錯字、數量與量詞、多品項、AND/OR、先說後改、取消與客製化、代詞、連續補充、背景聊天、超出點餐範圍。新菜名／價格／庫存從執行時資料供應，避免訓練成模型記憶的真相；換菜名、換菜單 ID 也應能通過。教師標註與合成擴增需人工覆核，既有 Main Agent 失敗軌跡不能直接當正確教師答案。

以原始對話／語句模板家族／說話者分組拆分 train、validation、test，避免同句改寫跨集合；另外保留新菜單、未見菜名與獨立真實 ASR 的測試切片。門檻與超參數只用 validation 選擇，凍結 test 不反覆調參。產品範圍外資料作為拒絕負例，不需要訓練回答那些問題。

比較方案時固定相同情境與起始狀態，分別記錄：

- 自動執行覆蓋率、其中錯誤變更率、澄清率、升級率、範圍外誤接受率；按 ADD／REMOVE／REPLACE 等操作分開。
- 完整操作與最終購物車是否正確；不得讓「只刪除尚未新增」算作成功替換。
- 冷／熱啟動端到端 p50／p95、首次可用回覆、模型與工具輪數、timeout 及峰值記憶體。timeout 計入失敗／未完成並另列原因，不從速度樣本中無聲刪除。
- 安全拒絕、正常完成、部分完成、基礎設施失敗分開；重試另外報告，不能洗掉首次失敗。
